## 1. Goal

A single coordinated release that (a) polishes the UI per direct user feedback, (b) makes the app **multi-game aware** (Unturned now, CS2 "coming soon"), (c) adds a **GitHub-driven changelog + auto-update**, (d) adds a **website promo**, and (e) completes the **live-memory detector set** (4 remaining detectors).

Three guiding constraints:
- The app already **auto-detects per-OS capability** (`capability-service.ts`); we surface and extend that, we don't reinvent it.
- The 4 new live detectors are **Windows-only native code** — built and unit-tested here, but end-to-end *verified by the user on Windows with the game running*.
- Startup must not pile up modals: the game picker, update prompt, and promo are **sequenced**, not stacked.

## 5. Group D — Multi-game architecture

### 5.1 Data model (`src/shared/games.ts`, shared so main + renderer agree)

```ts
export type GameId = 'unturned' | 'cs2'

export interface GameMeta {
  id: GameId
  name: string            // "Unturned", "Counter-Strike 2"
  available: boolean      // false → "Coming soon", picker option disabled
  processNames: string[]  // e.g. ["Unturned.exe"] — used by the live process-locator
}

export const GAMES: Record<GameId, GameMeta> = {
  unturned: { id: 'unturned', name: 'Unturned', available: true,  processNames: ['Unturned.exe'] },
  cs2:      { id: 'cs2',      name: 'Counter-Strike 2', available: false, processNames: ['cs2.exe'] }
}
```

### 5.2 Selection state (`src/renderer/stores/game-store.ts`, zustand)

- `selectedGame: GameId | null`, `setSelectedGame(id)`.
- Per requirement, the picker is shown **every launch** → `selectedGame` starts `null` each session.
- Last choice may be persisted only as the **default highlight** in the picker (nice-to-have; not required).

### 5.3 Game picker (`src/renderer/components/GamePicker.tsx`)

- Center modal shown when `selectedGame === null` at startup; blocks the app behind it.
- Cards for each game; CS2 rendered **disabled** with a "Coming soon" badge (no select).
- Selecting Unturned sets `selectedGame` and dismisses.

### 5.4 Active-game indicator

- Small chip in the title bar (near the `custos` wordmark) showing the active game name. Display-only — since the picker runs every launch, no in-app re-pick control is required.

### 5.5 Scoping

- Forensic scanners and the live scan are scoped to the selected game's config. Only Unturned is functional; CS2 is gated at the picker, so the rest of the app always runs against Unturned for now.
- The live `process-locator` uses `GAMES[selectedGame].processNames` instead of a hardcoded Unturned list.

## 6. Group C — GitHub changelog, auto-update, promo

### 6.1 GitHub service (`src/main/services/github-service.ts`, main process)

- `const REPO = 'dybeky/custos'`
- `getRecentCommits(perPage = 30)` → `GET https://api.github.com/repos/dybeky/custos/commits?sha=main&per_page=N`
- `getLatestRelease()` → `GET .../releases/latest` → `{ tagName, name, body, htmlUrl, publishedAt }` or `null` on 404 (no releases yet).
- Uses Node `fetch` (available in Electron 42's Node runtime) with an `AbortController` timeout (~8s) and required headers: `User-Agent: custos-app`, `Accept: application/vnd.github+json`.
- **Per-session cache** + graceful failure (GitHub unauthenticated limit is 60 req/hr; two calls/launch is fine). On error, the renderer shows a friendly "couldn't load" state, never a crash.
- Runs in **main**, so the renderer CSP (`connect-src` already allows `api.github.com`) is not even involved.

### 6.2 Changelog humanizer (`src/main/services/changelog.ts`, pure → unit-tested)

- `parseCommit(message)` → `{ type, scope, summary }` from conventional-commit prefixes.
- Friendly grouping:
  - `feat` → ✨ **New**
  - `fix` → 🐛 **Fixes**
  - `perf` → ⚡ **Performance**
  - `build` / `refactor` / `chore` / `docs` / `test` / `ci` / `style` → 🔧 **Improvements**
- Strip prefix + scope, capitalize, drop merge commits and noise. Returns grouped, display-ready entries.
- Dashboard renders a styled **Changelog card** (grouped, aurora-styled) via `window.electronAPI.getChangelog()`.

### 6.3 Auto-update (`update-check` flow)

- On launch (after the game picker), main compares `app.getVersion()` to the latest release tag.
- `compareSemver(a, b)` — small local comparator (no new dependency), **unit-tested**; tags normalized by stripping a leading `v`.
- If newer → renderer shows an **Update modal** (`components/UpdateModal.tsx`): humanized release notes (reuse the changelog humanizer on the release body or commits since current version) + **Download** (opens `htmlUrl` via `openExternal`) + **Later** (dismiss). Checked **once per session**.
- If the repo has **no releases**, update-check is a no-op (returns "no update"); the dashboard changelog still works from commits.

### 6.4 Promo toast (`components/WebsitePromoToast.tsx`)

- **Small bottom-right toast** (not a center modal — matches "small popup"), shown **every launch**, auto-dismisses after ~6s with a shrinking countdown bar.
- Creative copy promoting `https://97437.dev`; **Visit** button (`openExternal`) + ✕.
- Sequenced **after** any update modal so they never overlap.

### 6.5 Startup choreography (`App.tsx`)

1. Settings load.
2. **Game picker** (center, required) → user picks Unturned.
3. App content renders; **update check** fires in the background.
4. If update available → **Update modal**.
5. After the update modal closes (or immediately if none) → **promo toast** (auto-dismiss).

## 7. Group E — 4 remaining live detectors

All implement the existing `LiveDetector` interface (`{ id, name, run(ctx): Promise<LiveFinding[]> }`) and register in `live-orchestrator.ts`'s `DETECTORS` array next to `injectedModuleDetector` + `selfIntegrityDetector`. Pure decision functions are split out and unit-tested (the established pattern in `injected-module-detector.ts`); native memory/thread access is verified by the user on Windows.

### E1 — AOB memory signature scan (`detectors/aob-detector.ts`) — **top detector**

- Reads `ctx.signatures.aob` (array of `{ name, pattern, module? }`). Patterns are hex bytes with `??` wildcards.
- For each signature, scan the target module (or committed regions if `module` empty) via `memoryjs.findPattern` (wrapped in `native/memory.ts`). A hit → **high-confidence** finding with the signature name + address.
- **Pure/unit-tested:** pattern validation/parsing (hex + wildcards), match-on-buffer logic against fixtures.
- Ships with `aob: []` (empty); the user supplies byte patterns from cheat samples, exactly like the keyword list. Empty list → logs "0 signatures" and no-ops.

### E2 — Thread start-address check (`detectors/thread-detector.ts`)

- `native/winapi.ts` (koffi): `CreateToolhelp32Snapshot(TH32CS_SNAPTHREAD)` → enumerate the game PID's threads → `OpenThread` + `NtQueryInformationThread(ThreadQuerySetWin32StartAddress)` for each start address.
- Flag threads whose start address is **outside every loaded module's `[base, base+size)`** range (modules from `listModules`) — a hallmark of injected/manual-mapped code. Confidence: suspicious.
- **Pure/unit-tested:** `isAddressInAnyModule(addr, modules)` range check.

### E3 — IAT / inline hook check (`detectors/hook-detector.ts`) — most code, last

- Parse the game module's PE headers from memory (`readMemory`), locate the **IAT**, read each imported function pointer, and verify it points **into the exporting module's address range** (a pointer redirected elsewhere = IAT hook).
- **Inline hooks:** read the first bytes of selected critical functions; detect a trampoline prologue (`E9` JMP / `FF 25` indirect JMP / `68…C3` push-ret, etc.).
- **Pure/unit-tested:** PE-header parsing from a buffer, prologue-pattern detection from bytes (fixtures). Native: `readMemory` only.

### E4 — Mono enumeration + debugger-agent flag (`detectors/mono-detector.ts`) — Phase A now

- **Phase A (build now, high-signal):** detect the Mono **soft-debugger agent** — scan the game's command line / module flags for `--debugger-agent=` (managed debugger attached, common in cheat dev) and flag `mono*` modules loaded from non-standard paths.
- **Phase B (scaffold only, deferred):** walk the Mono runtime (`mono_get_root_domain` → `mono_assembly_foreach`) to enumerate managed assemblies and flag non-game ones. Version-specific; left as a documented stub.
- **Pure/unit-tested:** command-line flag parsing + assembly-name classification.

### E5 — Game-aware live scan

- `process-locator.ts` uses `GAMES[selectedGame].processNames`. Live scan stays Windows + native-available gated (existing capability gating); CS2 never reaches it (disabled in picker).

## 10. Risks & honest constraints

- **GitHub rate limit** (60/hr unauthenticated): mitigated by per-session cache + graceful failure UI.
- **4 detectors are Windows-only** and unverifiable on this Mac — the user confirms real-world detection.
- **Heuristic false positives** (foreign threads, private-exec memory, hooks) can flag legit overlays/anti-cheat → findings are confidence-labelled (`high` / `suspicious` / `info`), consistent with existing live findings.
- **Startup modal fatigue:** mitigated by the sequenced choreography (§6.5) and making the promo a small auto-dismissing toast.
- **Electron `fetch` in main:** if unavailable in the target Electron/Node build, fall back to Electron's `net` module.
